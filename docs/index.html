01 / The reason

Understand it.
Then build it.

Engines can feel like black boxes when you only use the finished tools. ForgeKiln is a way to learn what sits underneath by building and questioning each part.

01

Learn by making

Turn concepts into small, working experiments instead of treating documentation as something to read once and forget.

02

Keep the pieces clear

Give each system a focused job, understandable interfaces, and room to evolve without unnecessary complexity.

03

Grow through iteration

Expect early ideas to change. Test them, learn from the rough edges, and improve the design when there is a reason to.

02 / Right now

A small start.
A real project.

ForgeKiln is at the experimental stage. The goal today is not to claim a complete engine, but to establish reliable foundations and understand the decisions behind them.

Early development

Currently exploring input handling.

The first experiments use C++ and the Windows API to read keyboard input. The interface and implementation are still evolving.

03 / The direction

Where we plan to go.

A direction, not a deadline-driven promise. Each step depends on what the previous step teaches us.

Stabilize the basics

Refine keyboard input, understand key states, and establish a repeatable build-and-test workflow.

Shape core systems

Explore clean interfaces and the boundaries between input, application logic, and other engine parts.

Connect the pieces

Investigate a window and update loop, then learn how systems communicate within a running application.

Build toward a usable engine

As the foundations mature, explore rendering and simple interactive demos. Scope will follow what proves practical.

04 / The approach

Simple by intention.

The point is not to make the biggest engine or to recreate every feature in an established tool. It is to make thoughtful progress and understand what gets built.

S

Simple over complex

Prefer the smallest design that solves the problem well.

I

Iteration over perfection

Make a useful first version, test it, and improve it with evidence.

U

Understanding over shortcuts

Use tools to help, but make sure the decisions and code remain understandable.

P

Practicality over hype

Choose features based on what the project needs, not what sounds impressive.

Follow the work

The best way forward is one system at a time.
